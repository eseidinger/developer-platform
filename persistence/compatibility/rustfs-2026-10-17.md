# RustFS provider verification — October 17, 2026

Pinned server and embedded official console image: `rustfs/rustfs:1.0.2` at
`sha256:7e948dad4748bda48f8985fda7195f8cf2e4259427011f6120acc2c9acf51587`.
The matching server source tag resolves to
`2b243d8659497778c2406cc844a490565ec13287`.
Server/official console license: Apache-2.0. These pins describe a disposable local
fixture; they are not a deployed-service acceptance record.

The native provider maps resource UUIDs to separate buckets with versioning and
hard byte quotas. Each credential generation has its own non-disclosed parent
identity, a bucket/mode policy, and an expiring service-account key. Data identities
receive explicit administration/STS/KMS denies. They cannot manage credentials,
bucket policies, versioning or bucket deletion. Resource deletion stays an
operator action after the common retirement and verified-backup gate.

The real fixture verifies two buckets, writer/reader access, retained old object
versions, foreign-bucket denial, read-only write/delete denial, service-account
issuance/retry/revocation, expiration, and rejection of self/foreign/root-parent
service-account creation and expiration extension. It sends a signed multi-MiB
upload and read through the credential-bound HTTP relay, checks the bytes, and
denies reconnection after lease revocation. It verifies measured versioned usage
and bounded, retryable version purge without deleting another resource.

Hard-quota verification sets a 16 MiB allocation, rejects a 17 MiB write, preserves
existing reads and authorized deletion, leaves the other bucket writable, then
accepts that write after an operator-side increase to 32 MiB. Quota readiness is
checked before provisioning completes; an unavailable quota baseline fails closed.
The fixture does not establish every multipart/concurrent-write quota edge case.

Release-specific API details found by actual execution:

- Native admin requests require a signed `X-Amz-Content-SHA256` header.
- Policy resource syntax requires S3 ARNs, including administrative deny
  statements; administration, STS and KMS action families use separate statements.
- Service-account deletion returns HTTP 400 when already absent; the preceding
  information lookup returns an unambiguous 404 for idempotent cleanup.
- Expired/revoked S3 keys and hard-quota rejection use `InvalidRequest` HTTP 400
  in this release. Permission-boundary tests separately require actual 401/403.
- Quota writes can report temporary unavailability until their baseline is ready;
  this must never be treated as a successful unrestricted write.

Official-console investigation: native scoped `ListBuckets` succeeds, including
a signed browser request through the candidate lease gateway. The pinned console's
Key Login then submits a signed STS exchange at `/` and does not complete with the
selected expiring service-account credential. The
[official STS contract](https://docs.rustfs.com/en/security-compliance/iam/sts)
explicitly excludes service accounts from `AssumeRole`. The implemented adapter therefore uses a separate scoped human console identity
and exact child-session mapping. Do not disclose operator credentials or
widen resource roles to make the UI log in. Native service-account Key Login is unsupported; the scoped adapter below provides the console path.

The candidate adapter now provisions a separate human-only, resource-scoped
console IAM identity. Its `AssumeRole` children are associated with the exact
native access key and SHA-256 of the returned token; no child secret/token is
stored in the platform catalog. Registration is bounded to 16 current sessions
per human generation and cannot extend the original lease deadline. The gateway
waits for the private relay to observe that exact association before returning
the native STS response. Token parent claims alone are insufficient for binding.
