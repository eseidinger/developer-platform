# Identity and access

Status: current Keycloak reference-deployment procedure.

Use this one-time procedure to introduce the supported Keycloak reference
identity provider to an existing deployed lab, establish the first individual
`platform-admin`, and remove the bootstrap path. It implements the identity
boundary selected in [ADR-004](../architecture/decisions/ADR-004-identity-and-access-management.md);
it does not complete the Phase 1B acceptance tasks by itself.

Run host commands from the installation directory, normally
`/opt/developer-platform`, using a privileged shell. Do not put Keycloak
passwords, OIDC access tokens, or user subject IDs in Git, inventories, shell
history, tickets, or shared evidence.

## Prerequisites

1. Choose an identity hostname, for example `identity.example.com`, and create
   DNS pointing it to the platform host. The hostname must be reachable over
   HTTPS for user login and issuer validation.
2. Set `platform_identity_domain: identity.example.com` in the Ansible
   inventory. The [deploy playbook](../../ansible/deploy.yml) writes it as
   `IDENTITY_DOMAIN` on every deployment.
3. Confirm the host has a current encrypted backup and that no backup or
   availability drill is running. Deployment intentionally interrupts Compose
   services and may trigger the external heartbeat alert.
4. Use a named individual for the first administrator. Do not bootstrap a
   shared account or reuse the retired `PLATFORM_TOKEN`.

## Deploy the identity-provider configuration

From the updated controller checkout, deploy with the normal inventory:

```bash
ansible-playbook -i ansible/inventory.yml ansible/deploy.yml --ask-become-pass
```

On an existing pre-OIDC lab, the first run can fail its final API readiness
check because `PLATFORM_BOOTSTRAP_SUBJECT` has not yet been set. This is
expected: the playbook has already copied the source, generated any newly
required audit/Keycloak secrets without replacing existing secrets, and started
Keycloak. Do not work around this by enabling the legacy bearer token.

On the host, confirm Keycloak is running and that its public issuer is
reachable. Substitute the configured identity domain:

```bash
cd /opt/developer-platform
docker compose ps keycloak keycloak-db-init proxy
curl --fail --silent --show-error \
  https://identity.example.com/realms/platform/.well-known/openid-configuration >/dev/null
```

If the issuer is not reachable, correct DNS, firewall, Caddy/TLS, or the
Keycloak startup failure before creating an administrator. Inspect logs without
copying passwords or tokens:

```bash
docker compose logs --tail=100 keycloak proxy platform-api
```

## Create the first individual administrator

1. Open `https://identity.example.com` and select **Administration Console**.
2. Sign in as `admin` using `KEYCLOAK_ADMIN_PASSWORD` from the host's protected
   `.env`; do not export or display it in a terminal transcript.
3. Select the `platform` realm, create an enabled individual user, set that
   person's initial password, and copy the user's immutable **ID** (the OIDC
   `sub`). Do not use a mutable username or email address.
4. In a privileged editor, add exactly this value to the host `.env`:

   ```dotenv
   PLATFORM_BOOTSTRAP_SUBJECT=<individual-keycloak-user-id>
   ```

   Keep the file mode `0600`. This setting is host configuration, not an API
   credential. It is consumed only when no bootstrap grant record exists.

## Create and remove the one-time platform grant

Recreate the API container so it reads the new environment value:

```bash
cd /opt/developer-platform
bash scripts/up.sh
curl --fail-with-body http://127.0.0.1:8000/readyz
```

At startup, the API records the immutable issuer/subject principal and creates
its first persisted `platform-admin` grant. It also writes a durable bootstrap
audit event. Once readiness succeeds, remove `PLATFORM_BOOTSTRAP_SUBJECT` from
`.env` with a privileged editor and recreate the API container so the value is
not retained in its environment:

```bash
cd /opt/developer-platform
docker compose up -d --force-recreate platform-api
curl --fail-with-body http://127.0.0.1:8000/readyz
```

Do not use `docker compose restart platform-api` for this cleanup: restart does
not reload Compose environment values. Do not remove the Keycloak or audit
passwords generated by `scripts/init.py`.

## Verify and record

Use the [human access and authorization validation runbook](validation/access-and-authorization.md) to
obtain a PKCE Device Authorization token for the new administrator and verify
`GET /projects`. Then grant roles through the platform API; Keycloak authenticates
people, while platform-owned PostgreSQL grants remain authoritative for
authorization.

Record the deployed revision, identity hostname, timestamp, a private
administrator-reference identifier (not the raw subject), successful readiness
result, and redacted authorization/audit evidence in the delivery backlog. Continue with the role,
revocation, audit-export, and security-alert checks; do not mark Phase 1B closed
from bootstrap alone.

## Hosted application access installation and recovery

The hosted-access implementation has deployed core evidence: node-01 run
`c927adee1d50` passed all 39 named checks, including timed token expiry, on
October 11, 2026 ([EV-45](../maintainers/delivery/backlog.md#verification-register)).
The [run record](validation/access-and-authorization.md#executed-hosted-access-core-acceptance-october-11-2026)
lists the nine deferred checks; full PLAN-009/F-10 acceptance remains open.
Hosted access is not authorization to manage this Platform API. Follow the
[hosted application API guide](../developers/api.md#hosted-application-access)
for groups, enrollment, policy intent, service approvals, and managed-secret
delivery. Project-scoped application-access screens are implemented in portal
source, but their deployed approval journey has not yet been accepted (PLAN-020).

The supported `scripts/up.sh` installation now builds and imports the authorizer
image, installs two authorizer replicas in `platform-access`, and applies their
restricted network policies. `PLATFORM_API_IP` and `KEYCLOAK_IP` default to
`172.30.80.11` and `172.30.80.12`. Bootstrap starts the fixed-address core before
the remaining Compose services and checks live address ownership. The shared
network still has a dynamic pool: do not attach unrelated containers to it or
assign its fixed addresses elsewhere. A conflict owned by an old Compose service
is recovered using `ansible/deploy.yml`, which removes Compose containers without
removing data volumes or the k3d network; a conflicting k3d or unrelated container
requires operator review. Validate custom fixed addresses with
`python3 scripts/check-network-addresses.py --validate-only` before deployment.
The bootstrap sends derived internal and session keys straight to
Kubernetes Secret input, never to a manifest file. Keep `DATABASE_KEY` and the
encrypted backup containing it protected; changing that key changes derived
credentials. OAuth2 Proxy is digest-pinned to the tested 7.15.1 image. Browser
proxy configuration is generated per policy, not supplied by applications.

Keycloak remains one `platform` realm. The trusted credential provisioner now
needs `manage-clients`, `manage-users`, and `view-users` to project application
clients and memberships. It is infrastructure authority, not an application
credential. New browser clients include Keycloak's `basic` subject mapper in
addition to the minimal profile/email scopes; an email address is not the
authentication key or a membership approval.

A `v1alpha2` public ingress routes to the shared boundary, never directly to its
backend. The public pod accepts traffic only from authorizer pods. Missing,
pending, staging, and expired policies deny access. Reapplying a component
deployment removes historical `<component>-public` direct ingress routes.
Legacy single-service declarations retain their existing routing behavior;
they must migrate to `v1alpha2` before using hosted access. Do not claim they are
protected by this new capability. Keep the edge HTTPS-only externally.

For browser state changes, frontend code copies the readable
`__Host-platform-csrf` cookie into `X-Platform-CSRF-Token` and sends the exact
same HTTPS Origin. The session and signed activity cookies are HTTP-only.
Deleting the activity cookie cannot extend the eight-hour absolute session or
30-minute idle limit. Application responses cannot replace boundary cookies.
Group changes use a two-second catalog poll, four-minute browser claim refresh,
and five-minute token/snapshot maximum. An unavailable dependency never extends
the original snapshot deadline. Policies stage non-authorizing, await the
browser proxy and acknowledgements from every ready authorizer replica, then
activate; this initial conservative strategy can briefly deny all application
traffic during a policy update.

The isolated restore script sets a durable `recovery-required` flag before
starting services. Hosted routes remain denied until an authenticated human
platform administrator invokes `POST /operator/application-access/recover`.
This invalidates browser sessions, rotates potentially restored active or
provisioning machine credentials, and reconciles approved catalog membership
outward. Pending/rejected requests receive no grant. Poll the returned
`operationIds`, and confirm authorizer readiness before admitting traffic.
For a manual database restore, keep the application edge closed, apply the same
recovery quarantine, invoke recovery, and restart the authorizer deployment to
discard snapshots from the newer pre-restore generation. Never restore the
database underneath authorizers while leaving public application traffic open.

Retirement immediately excludes the project and its cross-project service
bindings from snapshots and queues provider cleanup. This also removes
application-owned ingress/proxy objects from the shared namespace; it never
deletes `platform-access` itself. Missing retired project namespaces do not
block client cleanup. Permanent project purge waits for hosted-access cleanup,
as well as deployment-credential cleanup, before deleting the catalog.
